# V2.0.8 — Production authentication and authorization boundary\n\nV2.0.8 replaces the temporary in-process credential/session implementation with Supabase Auth while preserving the provider-neutral Engineering Core.\n\n## Architecture\n\nSupabase Auth\n      ↓\n@supabase/ssr / Next.js Proxy\n      ↓\nSupabase JWT claims\n      ↓\nserver-controlled app_metadata\n      ↓\nAuthenticatedIdentity\n      ↓\nexisting Engineering authorization policy\n      ↓\nprotected engineering routes\n\nThe core principle remains:\n\n> The identity provider authenticates. The Engineering authorization policy decides what the identity may do.\n\n## Implemented\n\n- Supabase Auth email/password authentication.\n- @supabase/ssr cookie-based SSR sessions.\n- Next.js 16 proxy.ts refreshes and validates Supabase sessions with getClaims().\n- Protected /projects/* pages and non-auth /api/* routes.\n- Explicit authorization checks inside protected engineering route handlers.\n- Engineering roles are read only from server-controlled Supabase app_metadata.\n- Existing deny-by-default V2.0.6 authorization policy remains the authorization source of truth.\n- Authentication and authorization decisions continue to emit V2.0.7 audit events.\n- No Supabase secret/service-role key is required by the application runtime.\n\n## Engineering role claims\n\nAuthorization metadata must be stored in Supabase app_metadata, never user_metadata.\n\nExample:\n\n    {\n      "engineering_roles": ["ENGINEER"],\n      "engineering_project_ids": ["PROJECT-ID"]\n    }\n\nSupported roles:\n\n- ENGINEER\n- REVIEWER\n- ADMIN\n- AGENT\n\nAn authenticated Supabase user with no valid engineering role fails closed.\n\nProject IDs are currently supported when supplied in app_metadata. Durable multi-user project membership belongs to V2.0.9 and will move project authorization into Supabase/Postgres RLS rather than relying on JWT project lists.\n\n## Deployment configuration\n\nSet:\n\n- NEXT_PUBLIC_SUPABASE_URL\n- NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY\n\nThe publishable key may be exposed to the browser. Supabase secret/service-role keys must never be placed in NEXT_PUBLIC_* variables or committed to the repository.\n\nFor the new Engineering Workspace project:\n\n- Supabase project: AI Mechanical Engineering Assistant\n- Project ref: mepmogsqhxxasahwhete\n- Region: eu-west-3\n\nCreate the first engineering user through Supabase Auth, then assign the appropriate app_metadata role through a trusted server/admin workflow. Do not use client-controlled profile metadata for authorization.\n\n## Verification boundary\n\nThe Next.js Proxy is the first authentication gate, not the complete authorization layer. Protected route handlers re-check identity and permission before executing engineering work. This follows Next.js guidance that authentication/authorization should not rely solely on Proxy.\n\nV2.0.9 will add durable project membership, Postgres RLS, and multi-user workspace authorization.
